## 断言写法约定（SYS-1）

全计划的 convergence.criteria 一律按以下三条写，避免「命令本身不成立」把正确
实现判成失败：

1. **否定型断言**一律写作
   `test -e <PATH> && [ "$(rg -c '<PAT>' <PATH> | wc -l)" -eq 0 ]`
   —— 路径不存在时 `test -e` 先失败即判定 FAIL，不会因为「文件没了所以也没匹配」
   而误判通过。不得写成 `rg -vc`：计数为 0 时它无输出且退出码 1，通过态根本无法产生。

2. **计数型断言**一律写作
   `[ "$(rg -c --no-filename '<PAT>' <PATH> | awk '{s+=$1} END{print s+0}')" -ge N ]`
   —— `--no-filename` 保证对目录也只输出数字，`awk` 求和保证多文件时得到总数。

3. **禁止 `grep -rc`**（对目录输出多行 `file:count`、对缺失路径退出码 2）；
   **禁止正则 look-around**（ripgrep 的 Rust regex 不支持，实测退出码 2）。

### 关于 UI 状态为何是「未验证」

第 1～14 项需要在真实 GUI 里人工点击确认，本轮执行环境无法驱动 Electron 窗口
交互；第 15 项按计划约定，**在没有 clean VM 的情况下只记 packaged-smoke**
（即只在开发机上验证产物可启动，不承诺干净系统上的依赖完整性）。

这些项目的自动化替身是 `tools/fake-pi/` 提供的 fake Pi RPC 进程 —— 它按
`docs/rpc.md` 的事件格式吐出 `text_delta` / `thinking_delta` / `toolcall_end` /
`tool_execution_start|end` / `extension_ui_request`，使第 1、2、3、10 项的**协议层**
回归可在无真实 Provider 的前提下自动跑通（见 `packages/pi-sdk/test/client.spec.ts`）。
渲染层的人工确认在有 GUI 的环境里补做，结果回填本表。

### fake Pi 的 9 个场景

| 场景 | 行为 | 用于验收 |
|------|------|----------|
| `normal` | 完整流式序列：thinking → text → toolcall → tool 执行 | 第 1、2、3 项 |
| `malformed-json` | 先写一行截断 JSON 与一行纯文本噪声，再写合法 response/event | 坏行必须被跳过 |
| `timeout` | 吞掉全部命令，永不回响应 | 挂起/超时处理 |
| `stderr-noise` | 启动即向 stderr 写诊断噪声 | stderr 不得被当成协议 |
| `exit-immediately` | 启动即 `exit(0)` | 进程启动即死 |
| `crash-mid-stream` | 流到一半 `exit(1)`，濒死后不再应答 | 在途请求必须被 reject |
| `extension-ui` | 发出 `select` 请求并等待 `extension_ui_response` | 第 10 项 |
| `stale-generation` | abort 响应之后延迟 300ms 再吐旧代际事件 | 代际丢弃 |
| `oversized-line` | 单行 16 MB JSON | JSONL buffer 上限 |

**分帧硬约束**：读写两侧都只以 LF (`\n`) 分帧、容忍尾部 `\r`，禁止使用 Node
内置的通用行读取模块 —— 它还会按 U+2028 / U+2029 分行，而这两个码位在 JSON
字符串里是合法内容（`docs/rpc.md` 的 Framing 章节逐字禁止）。
